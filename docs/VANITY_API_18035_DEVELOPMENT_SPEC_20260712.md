# TRON Vanity API 18035 开发说明书（评审稿）

- 文档日期：2026-07-12
- 文档状态：待用户评审，尚未开始接口开发
- 项目性质：独立新业务，不替换现有生产接口
- 客户数量：第一阶段仅一个固定客户
- 客户端口：`18035`
- 计算资源：Vast Secure Cloud 固定 RTX 5090
- 核心版本：独立 V2 Round52 适配核心

## 1. 硬边界

1. 不修改、不替换、不重启现有 `18030` 和 `18031`。
2. 不修改现有 RunPod Endpoint、镜像、worker 或客户调用逻辑。
3. 新服务使用独立目录、进程、systemd、配置、日志、数据库和端口。
4. 未经用户明确批准，不开放 AWS `18035` 防火墙规则、不部署远端服务。
5. 本文档确认前只允许继续完善文档，不开始接口代码和生产部署。
6. 私钥、API key、token、Age identity 不得出现在聊天、日志、任务文件或管理界面。

## 2. 业务目标

使用一张长期运行的 RTX 5090 同时处理三类任务：

```text
P0：T + 后5，实时同步返回
P1：包含自定义前缀的6/7/8位任务，后台运行并回调
P2：纯后缀6/7/8位任务，最低优先级后台运行并回调
```

客户只使用一个提交入口，不需要理解或提交 `P0/P1/P2`。服务端根据请求内容自动分类。

## 3. 已验证核心基线

### 3.1 正确性

- 已覆盖自定义总长度6、7、8的全部24种前后缀拆分。
- 已在 RTX 5090 上通过24/24 GPU强制命中向量。
- 已通过1、4、8、16个目标的隔离验证。
- 命中结果必须由独立CPU逻辑重新派生并验证后才能交付。

### 3.2 RTX 5090代表性速度

| 类型 | 当前实测或代表性速度 |
| --- | ---: |
| P0 `T*后5` | 稳定约 `3.69-3.77B/s`，峰值样本约 `4.03B/s` |
| P1 含前缀组合 | 代表性实测约 `5.3-5.5B/s` |
| P2 纯后6/7/8 | 代表性约 `3.6-3.77B/s` |
| 16个兼容目标合批 | 代表性实测约 `5.07B/s` |

说明：

- P1可以利用前缀早筛，避免大量候选继续执行完整checksum路径。
- P2没有前缀早筛，天然比P1慢。
- 不能把P1和P2放进同一个GPU批次，否则纯后缀会破坏P1的早筛收益。
- 不是所有24种组合都单独租卡测速；未单测组合使用相同CUDA路径的代表性区间，不能作为精确SLA。

### 3.3 接管能力

当前一组有界GPU任务实测：

```text
P50：13.479ms
P99：13.515ms
最大：13.515ms
```

调度器完成后必须重新执行“无调度器 vs 有调度器”同机测试。调度造成的连续吞吐损失不得超过 `3%`。

## 4. 匹配规则与自动分类

### 4.1 字符集

所有自定义字符必须来自TRON Base58字符集：

```text
123456789ABCDEFGHJKLMNPQRSTUVWXYZabcdefghijkmnopqrstuvwxyz
```

- 区分大小写。
- 不允许 `0`、`O`、`I`、`l`。
- 地址固定首位 `T` 不计入自定义位数。

### 4.2 分类规则

| 分类 | 条件 | 示例 |
| --- | --- | --- |
| P0 | `prefix`为空，`suffix`恰好5位 | `T*Yqvi2` |
| P1 | `prefix`至少1位，且 `len(prefix)+len(suffix)` 为6、7或8 | `TLU*Yqvi2`、`TLU9wb2*` |
| P2 | `prefix`为空，`suffix`为6、7或8位 | `T*ABCDEF` |

不满足以上条件的请求直接拒绝，不进入任务队列。

## 5. 客户接口

### 5.1 网络边界

- 服务监听端口：`18035`。
- 生产必须启用TLS，禁止通过公网明文HTTP传输结果。
- 客户路由只依赖AWS源IPv4白名单，不要求客户提交API token。
- AWS防火墙只允许客户固定公网IPv4和Vast固定出口IPv4访问 `18035/TCP`。
- 客户公网IPv4变化时必须先人工更新白名单，禁止临时开放所有来源。
- 内部worker路由即使通过相同端口，也必须额外执行mTLS认证。
- Vast worker不直接向客户暴露端口。

### 5.2 统一提交入口

```http
POST /v1/find
Content-Type: application/json
```

客户不传优先级，服务端自动分类。

#### 单任务请求

```json
{
  "prefix": "LU",
  "suffix": "Yqvi2"
}
```

每个单任务固定只生成一个地址，不需要数量字段。

#### 后台批量请求

```json
{
  "items": [
    {"prefix": "", "suffix": "111111"},
    {"prefix": "", "suffix": "AAAAAA"},
    {"prefix": "LU", "suffix": "Yqvi2"}
  ]
}
```

约束：

- 批量请求只允许P1/P2任务。
- P0必须单独提交，避免同步和异步响应语义混合。
- 第一阶段单批最多 `1000` 个item，174个一次性纯后缀任务可以一次提交。
- API接收数量不受GPU每批16个目标的限制。

### 5.3 P0成功响应

P0等待GPU命中后使用HTTP `200`直接返回：

```json
{
  "status": "completed",
  "matched_address": "T...Yqvi2",
  "encrypted_private_key": "-----BEGIN AGE ENCRYPTED FILE-----...",
  "elapsed_ms": 238
}
```

### 5.4 P1/P2接单响应

P1/P2写入持久队列后使用HTTP `200`返回：

```json
{
  "status": "queued",
  "batch_id": "server-generated-id",
  "items": [
    {
      "item_id": "server-generated-id",
      "class": "P2",
      "status": "queued"
    }
  ]
}
```

客户不需要保持连接，命中后由服务端主动回调客户预先登记的固定接口。

### 5.5 错误响应

| HTTP | 错误码 | 含义 |
| ---: | --- | --- |
| 400 | `INVALID_PATTERN` | 长度、字符或结构非法 |
| 429 | `P0_BUSY` | P0并发已超过单卡同步承载上限 |
| 503 | `GPU_UNAVAILABLE` | GPU或worker不可用 |
| 504 | `P0_TIMEOUT` | P0内部任务超过硬时限 |

错误响应不得包含内部栈、命令、主机凭证或敏感结果。

## 6. P0同步任务设计

### 6.1 时间设计

| 项目 | 设定 |
| --- | ---: |
| 正常目标 | 尽量1秒内返回 |
| GPU任务硬超时 | `10s` |
| 服务端HTTP超时 | `15s` |
| 建议客户HTTP超时 | `20s` |
| 成功响应去重缓存 | `60s` |

单P0按当前速度理论平均命中约 `0.18s`、P90约 `0.41s`、P99约 `0.82s`。这些是概率估算，不是承诺SLA。

### 6.2 并发

- 同一GPU不启动多个互相争抢CUDA context的业务进程。
- 多个不同P0任务使用约13.5ms的有界计算组轮转，避免队头任务长期阻塞。
- 第一阶段 `P0_MAX_INFLIGHT=8`。
- 超过上限不继续堆积到客户超时，返回 `429 P0_BUSY`。
- 请求量增长后通过增加GPU实例扩容，不在单卡上无限增加并发。

### 6.3 服务端自动去重

客户不需要提交订单号。去重键为：

```text
customer_id + normalized_suffix
```

规则：

1. 相同后缀已有P0正在计算：新HTTP请求共享同一个内部GPU任务，不启动第二次搜索。
2. 多个连接同时等待同一内部任务时，命中后向所有仍在线的连接返回同一份加密结果。
3. 客户连接断开或客户侧超时不会取消内部GPU任务。
4. 客户重新请求相同后缀时，如果原任务仍运行，继续等待原任务。
5. 原任务已成功且完成不超过60秒：直接重放原加密响应。
6. 成功超过60秒后再次请求：创建新任务并生成新的地址。
7. GPU真实失败或内部10秒硬超时：清除运行状态，下一次请求允许重新计算。

这里的“共享任务”只发生在同一个固定客户的短期重复请求中。缓存只保存最终Age密文响应，不记录明文私钥。

## 7. P1/P2后台任务设计

### 7.1 队列优先级

```text
P0 实时 T+后5
  ↓ P0为空
P1 含前缀的6/7/8位后台任务
  ↓ P0和P1均为空
P2 纯后缀6/7/8位后台任务
```

- P0拥有绝对优先级。
- P1到达会暂停P2。
- P2是最低优先级的一次性或低价值库存任务，不长期预留固定GPU比例。
- P1持续有任务时，P2可能长期暂停；接口必须如实显示queued/paused，不能承诺固定完成时间。

### 7.2 GPU批次与队列容量

- `16`是单次GPU批次的活跃目标上限，不是API任务总量上限。
- P1、P2等待队列可以保存远多于16个任务。
- P1和P2不能混在同一个GPU批次。
- 同类兼容目标最多16个合批，共享ECC、Keccak和checksum主路径。
- 某目标命中后移除，并在下一个边界补入同类等待任务。
- 只有一个任务时立即运行，不等待凑满16个。

### 7.3 搜索进度

- 每个活跃批次使用明确的随机起点或搜索分片。
- 暂停时保存非敏感游标、分片和任务状态。
- 恢复后不得从已完成区间重新开始。
- worker重启允许丢失最近一个短批次的进度，但不能丢失订单或已命中的密文结果。

### 7.4 后台重复任务

- 相同pattern已有queued/running任务时，不创建第二个相同目标描述符。
- 每个item固定只生成一个地址。
- 同一pattern确实需要第二个不同地址时，等待第一个任务完成后重新提交。
- 数据库对 `matched_address` 设置唯一约束。
- 已完成任务再次提交可创建新任务，不复用旧私钥结果。

## 8. GPU调度器

### 8.1 单一GPU所有者

一个长期运行的worker独占CUDA context：

- CUDA context、预计算表和常量常驻。
- 禁止每个任务启动独立GPU进程。
- 禁止P0、P1、P2各自拥有独立CUDA context争抢显卡。
- API线程只提交任务，不直接调用CUDA热路径。

### 8.2 有界切片

- 后台核心在约 `10-20ms` 的计算组边界检查P0。
- 同一队列连续运行时不无意义地重载目标或重建上下文。
- 只有优先级变化、目标命中或公平轮换时才切换目标表。
- 调度器热路径不得同步写数据库、日志或网络。
- 状态和监控通过无阻塞队列交给独立线程处理。

### 8.3 性能保护

- 调度器吞吐损失验收上限：`3%`。
- P0接管GPU的P99等待上限：`20ms`。
- 调度器异常时自动停止P1/P2，只保留P0。
- GPU温度、驱动、Xid、功耗或频率异常时拒绝新P0并暂停后台任务。

## 9. 回调设计

### 9.1 固定配置

第一阶段只有一个客户：

- 回调URL由服务端配置，不允许请求体传入任意URL。
- 客户Age recipient由服务端配置，不允许请求覆盖。
- 客户回调防火墙只允许43服务器的固定公网IPv4访问。
- 回调必须使用HTTPS，43必须验证客户域名和TLS证书。
- 第一阶段不使用HMAC或其他回调认证密钥。
- 依赖IP白名单前，必须确认43已绑定不会因实例停止/启动而变化的静态公网IPv4。

### 9.2 命中回调

```http
POST {fixed_customer_callback_url}
Content-Type: application/json
```

```json
{
  "event_id": "server-generated-id",
  "batch_id": "server-generated-id",
  "item_id": "server-generated-id",
  "pattern": "TLU*Yqvi2",
  "matched_address": "T...Yqvi2",
  "encrypted_private_key": "-----BEGIN AGE ENCRYPTED FILE-----...",
  "completed_at": "2026-07-12T00:00:00Z"
}
```

- 每个回调包含时间戳和唯一事件ID。
- 客户根据43固定源IPv4白名单接收请求，不再校验HMAC签名。
- 客户以 `event_id` 幂等处理重复回调。
- 回调失败只重试传输密文结果，绝不重新搜索。
- 使用指数退避重试，并在管理数据中记录次数和最后错误。

## 10. 43与Vast通信及数据边界

### 10.1 通信方向

Vast worker主动连接43，43不主动连接Vast：

```text
Vast -> 43：领取/续租任务、提交心跳、提交加密结果
43   -> Vast：仅作为上述请求的HTTPS响应返回任务或确认
```

这样Vast不需要开放任何公网入站业务端口。内部路由建议为：

```http
POST /internal/v1/worker/lease
POST /internal/v1/worker/heartbeat
POST /internal/v1/worker/result
```

内部通信强制要求：

- TLS和双向证书认证（mTLS）。
- Vast固定出口IPv4白名单。
- Vast保持出站HTTP/2长连接或长轮询；43出现P0时立即结束等待并下发，禁止使用1秒级固定轮询。
- 长连接断开后使用带抖动的短退避重连，恢复后先同步未ACK结果再领取新任务。
- 每个请求携带时间戳、随机nonce、worker ID和唯一事件ID。
- 43拒绝过期时间戳、重复nonce、未知worker和重复事件。
- mTLS证书和内部认证材料独立轮换，不与客户接口共享。
- 所有内部响应和日志都不得包含明文私钥。

### 10.2 任务租约

- 43是任务唯一权威来源。
- Vast使用短租约领取P0/P1/P2任务，并通过心跳续租。
- 租约过期后43可以重新分配尚未完成的任务。
- worker重启后先向43重新同步任务，不能只相信本地状态。
- P0使用短期实时租约；P1/P2保存非敏感搜索分片和游标。

### 10.3 43上的权威数据库

第一阶段使用18035项目独立的SQLite WAL数据库，数据库写入由单一controller进程管理。它保存：

```text
批次与任务状态
P0去重状态和60秒密文响应缓存
P1/P2队列、租约、搜索分片和游标
matched_address
Age加密后的private key密文
回调outbox、重试次数和确认状态
```

约束：

- 数据库文件与18030/18031完全独立。
- 数据目录权限 `700`，数据库及备份权限 `600`。
- 定期执行一致性检查和加密备份。
- 数据库中禁止出现明文私钥、Age identity和内部认证密钥。
- 未来需要多个43控制节点时，再迁移到独立PostgreSQL；第一阶段不引入额外数据库服务。

### 10.4 Vast本地保存内容

Vast不保存完整业务数据库，也不是订单权威来源。为了断网时不丢失已经命中的结果，worker只保留一个最小本地SQLite WAL状态库：

```text
当前lease_id、item_id和任务类别
非敏感prefix/suffix目标描述符
非敏感搜索分片、游标和最后checkpoint时间
已经Age加密的待确认结果
matched_address、result_id和43确认状态
```

Vast明确禁止持久化：

```text
明文private key、WIF、seed或mnemonic
Age identity或客户解密密钥
客户callback URL
客户请求历史和完整业务订单库
Vast API key
```

本地状态规则：

1. 搜索进度通过异步线程低频checkpoint，不进入GPU热路径。
2. 命中后先CPU复核并Age加密，再将密文写入本地outbox。
3. Vast将密文结果提交给43。
4. 只有43完成权威数据库事务并明确ACK后，Vast才删除本地密文outbox记录。
5. Vast重启时可以从43重新领取任务，并重发所有未ACK的密文结果。
6. 本地状态库目录权限 `700`、文件权限 `600`，禁止进入镜像层和普通日志。

## 11. 私钥安全

### 11.1 强制边界

- 明文私钥只允许在Vast worker命中后的受控内存中短暂出现。
- worker使用固定客户Age recipient立即加密。
- Vast离开边界前只能输出 `matched_address + encrypted_private_key`。
- 43服务器只保存和转发Age密文，不接触明文私钥。
- GPU缓冲区、CPU临时标量和受控内存在加密后立即清零。
- 禁止core dump、swap、debug命中输出和私钥stdout/stderr。

### 11.2 安全上限

RTX 5090不提供本项目可依赖的硬件机密计算保证。Vast Secure Cloud只能降低宿主和运维风险，不能证明宿主管理员绝对无法接触进程或GPU内存。对客户不得宣传为“宿主零接触”。


```text
vanity-api-18035.service
```

要求：

## 14. 监控指标

允许记录：

- P0/P1/P2队列长度和状态。
- P0总耗时、GPU耗时、并发数、去重命中数。
- P1/P2活跃目标数、暂停时间和完成数量。
- GPU型号、温度、功耗、频率、利用率和Xid。
- 调度器接管延迟和吞吐损失。

- 明文私钥、候选标量或Age identity。
- 完整Age密文或内部认证材料。
- 请求认证头和内部服务认证材料。

## 15. 验收标准

### 15.1 正确性

- 24种6/7/8位拆分全部通过确定性GPU向量。
- P0、P1、P2分类测试100%通过。
- 每个命中结果都通过CPU独立复核。
- 非Base58字符和不可能前缀在进入GPU前拒绝。

### 15.2 并发与去重

- 100个同时到达的相同P0请求只创建一个GPU任务。
- P0客户端断开后内部任务继续，重试能够重新等待原任务。
- P0成功后60秒内重复请求不启动新GPU任务。
- 10秒硬超时后状态被清理，下一次请求可以重新计算。
- P1/P2提交超过16个目标时正确排队，不丢任务。

### 15.3 性能

- P0单任务吞吐不得低于已确认基线的 `95%`。
- 调度器相对连续核心的吞吐损失不超过 `3%`。
- P1/P2运行时P0接管GPU的P99不超过 `20ms`。
- 1、4、8、16目标分别实测，不用理论值替代。
- P1/P2不能因错误合批互相拖入错误性能路径。

### 15.4 可靠性与安全

- API重启不丢P1/P2订单和已命中的密文结果。
- worker重启不重复交付同一个地址。
- 回调失败不重新计算、不丢结果。
- Vast断网期间已Age加密的结果进入本地outbox，恢复后成功重发并在43 ACK后删除。
- Vast本地状态全部丢失后，仍能以43权威数据库恢复未完成任务。
- 日志、异常、任务文件、数据库和crash路径的私钥扫描结果为零。
- 新服务故障不得影响18030/18031健康状态和响应耗时。

## 16. 开发顺序

### Phase 0：文档确认

- 用户确认本文档。
- 本阶段不开放端口、不部署、不租GPU。

### Phase 1：独立项目骨架

- 创建18035独立目录、配置、数据库schema和边界测试。
- 加入禁止访问18030/18031和现有RunPod生产资源的自动检查。

### Phase 2：GPU调度器

- 实现P0/P1/P2分类器。
- 实现单CUDA context、16目标合批、暂停/恢复和搜索游标。
- 完成无调度器与有调度器同机性能对比。

### Phase 3：安全结果路径

- 实现命中复核、Age加密、受控内存清零和密文回传。
- 完成日志、异常、重启和crash泄漏测试。

### Phase 4：18035 API与P0去重

- 实现统一 `/v1/find`。
- 实现P0 singleflight、60秒响应缓存、10秒硬超时和并发上限。
- 实现P1/P2批量接单和持久队列。

### Phase 5：客户回调

- 实现固定URL、源IPv4白名单约束、幂等事件和密文重试队列。
- 完成客户测试环境端到端验证。

### Phase 6：Vast固定机与部署验收

- 先使用On-demand候选机完成性能和稳定性验收。
- 用户批准后再决定Reserved周期。
- 部署独立systemd，但暂不开放AWS防火墙。

### Phase 7：小流量开放

- 只对客户固定IPv4开放 `18035/TCP`。
- 先进行测试请求，再逐步开放真实业务。
- 对比开放前后18030/18031性能，确认零影响。
